# Deploying `app-web`

This guide assumes you've never deployed a Vite single-page app before. It
walks through building `app-web` for production and understanding how the
provided Docker image serves it. All commands are run from inside the
`app-web/` directory unless stated otherwise.

## 1. Prerequisites

- **Node.js 20.x**. This isn't pinned via a `.nvmrc` or an `engines` field
  in `package.json` in this project, but the repository's own CI
  (`.github/workflows/pr-checks.yml`) builds it with Node 20, and the
  Dockerfile's builder stage uses `node:20-alpine`. Use Node 20 to match
  both. Install it from [nodejs.org](https://nodejs.org/en/download) or,
  if you use `nvm`:
  ```bash
  nvm install 20
  nvm use 20
  ```
- **npm** (ships with Node). This project uses `package-lock.json`, so
  npm is the expected package manager (not yarn/pnpm), even though the
  Dockerfile has a fallback branch for a `yarn.lock` — see step 2.
- **Docker** (only if you're building/running the production container
  image locally, e.g. `Docker Desktop` or the Docker Engine on Linux).

## 2. Install dependencies

From `app-web/`:

```bash
npm ci
```

`npm ci` is used (not `npm install`) because a `package-lock.json` is
committed to the repo. `npm ci` installs the exact versions from the
lockfile and fails fast if `package.json` and the lockfile have drifted
apart — this is what both CI (`pr-checks.yml`) and the Dockerfile's
builder stage do, so use it locally too for a build that matches what
actually ships.

## 3. Build for production

```bash
npm run build
```

Confirmed from `package.json`:
```json
"build": "tsc && vite build"
```

So `npm run build` **type-checks the whole project with `tsc` first**,
then runs `vite build`. If there are any TypeScript errors, the build
fails before Vite ever runs — type-checking is part of the build gate,
not a separate optional step. This matches the comment in this repo's own
CI (`.github/workflows/pr-checks.yml`): *"`build` runs `tsc && vite
build`, so typecheck is part of the gate."*

## 4. Build output

Vite's default output directory is `dist/`, and this project doesn't
override that in `vite.config.mts` — confirmed by both the Vite default
and the Dockerfile, which copies `/app/dist` out of the builder stage (see
below). `dist/` is listed in `.gitignore`, so it's never committed; it's
regenerated by every build.

The `dist/` folder is a fully static bundle (`index.html`, hashed JS/CSS
assets, and copies of everything in `public/`). It can be served by any
static file server — no Node process needs to run in production.

## 5. How the Docker image serves it

The repo's `Dockerfile` is a two-stage build:

```dockerfile
FROM node:20-alpine AS builder
WORKDIR /app
COPY package.json package-lock.json* yarn.lock* ./
RUN if [ -f yarn.lock ]; then yarn install --frozen-lockfile; \
    else npm ci; fi
COPY . .
RUN if [ -f yarn.lock ]; then yarn build; else npm run build; fi

FROM nginx:1.27-alpine
RUN apk add --no-cache gettext
COPY --from=builder /app/dist /usr/share/nginx/html
COPY nginx.conf.template /etc/nginx/templates/default.conf.template
EXPOSE 80
```

**Stage 1 (`builder`)** installs dependencies with `npm ci` (there's no
`yarn.lock` in this project, so the `yarn` branch never actually runs
here) and then runs `npm run build`, producing `/app/dist`.

**Stage 2** is a plain `nginx:1.27-alpine` image. It copies the built
`dist/` folder into nginx's web root (`/usr/share/nginx/html`) and copies
`nginx.conf.template` into nginx's **templates** directory
(`/etc/nginx/templates/default.conf.template`).

That "templates" directory is a feature of the official nginx Docker
image: on container startup, its entrypoint script runs every `*.template`
file it finds there through `envsubst` (environment-variable
substitution) and writes the result into `/etc/nginx/conf.d/`, where nginx
actually loads it from. That's why the Dockerfile installs the `gettext`
package — `envsubst` is part of it.

To build and run the image locally:

```bash
docker build -t app-web:local .
docker run -p 8080:80 -e BACKEND_URL=https://api.dev.trovo.app app-web:local
# then open http://localhost:8080
```

### What `nginx.conf.template` actually does

```nginx
location /api/ {
  proxy_pass ${BACKEND_URL}/;
  ...
}

location /ws/ {
  proxy_pass ${BACKEND_URL}/;
  ...
}

location / {
  try_files $uri $uri/ /index.html;
}
```

At container startup, `${BACKEND_URL}` in this file is substituted with
the **`BACKEND_URL` environment variable** set on the container (e.g. via
`docker run -e BACKEND_URL=...`, or however the container is deployed in
your orchestrator/Portainer). The result is nginx configuration that:

- Serves the built SPA for any normal route, falling back to
  `index.html` for client-side routing (`try_files ... /index.html`).
- Reverse-proxies same-origin `/api/*` and `/ws/*` requests through to
  the real `app-backend` at `$BACKEND_URL`.

This is the one piece of **genuine runtime configuration** in this app:
`BACKEND_URL` is read by nginx when the container starts, not baked into
the JS bundle. It's separate from — and takes priority in production
over — the `VITE_API_URL` / `VITE_SOCKET_URL` build-time variables
described below.

### Build-time vs. runtime configuration (the tricky part)

Vite, like Create React App before it, **inlines `import.meta.env.VITE_*`
variables into the JS bundle at build time**. Once `npm run build` has
run, those values are baked into the static files in `dist/` — changing
an environment variable afterwards (e.g. at container `docker run` time)
has **no effect** on them, because there's no server-side process left to
re-read the environment. This trips up a lot of people coming from
server-rendered apps.

In this project specifically:

- **`VITE_API_URL`** and **`VITE_SOCKET_URL`** (see `src/store/config.ts`)
  are read via `import.meta.env` — these are **build-time-baked-in**. If
  unset, the code falls back to same-origin `/api` and `/ws/v1`:
  ```ts
  export const BASE_URL = import.meta.env.VITE_API_URL ?? '/api';
  export const SOCKET_URL = import.meta.env.VITE_SOCKET_URL ?? `wss://${wsHost}/ws/v1`;
  ```
  This fallback is what makes the production/Docker setup work without
  setting `VITE_API_URL` at all: the built app calls relative `/api` and
  `/ws/v1` paths, and nginx (using the **runtime** `BACKEND_URL` variable
  described above) proxies those through to the real backend. So in this
  particular app, the frontend's own build rarely needs to know the
  backend's address — that indirection is handled by nginx at runtime
  instead.
- **`BACKEND_URL`**, by contrast, is **genuinely runtime-configurable**:
  it's consumed only by `nginx.conf.template`'s `envsubst` step at
  container start, never by the JS bundle itself.

Practical implications:
- If you need the built app to call a backend directly from the browser
  (bypassing the nginx proxy), you must set `VITE_API_URL` /
  `VITE_SOCKET_URL` **before running `npm run build`**, and rebuild for
  each target environment (dev/staging/prod) that needs a different
  value.
- If you're happy with the same-origin `/api` + nginx-proxy setup (the
  normal production path), you only need to set `BACKEND_URL` on the
  container at deploy time — no rebuild required per environment.
- See [`CONFIGURATION.md`](./CONFIGURATION.md) for the full variable
  list.

## 6. A note on this repo's CI workflows

`/home/user/src-monorepo/.github/workflows/deploy.yml` and
`pr-checks.yml` both filter their "web" jobs on the path prefix
**`web/**`** (e.g. `working-directory: web`, `paths: - 'web/**'`).

This project's actual directory in the monorepo is **`app-web/`**, not
`web/`. As written, those path filters will **not** match changes made
under `app-web/`, so pushes/PRs touching this project may silently skip
the CI jobs and the build-and-push step that (per `deploy.yml`'s own
comments) builds this Dockerfile and pushes it to DigitalOcean Container
Registry, from where Portainer redeploys it.

This strongly suggests those workflow files were copied from, or written
for, a differently-laid-out sibling repository (one where the frontend
lives at `web/`) and haven't been updated for this monorepo's actual
`app-web/` naming. **Treat `deploy.yml` / `pr-checks.yml` as unreliable
for this project until that path mismatch is fixed** — don't assume CI is
actually building or deploying `app-web` on every change just because
these files exist. The build and Docker steps described above were
verified directly against this project's own `package.json` and
`Dockerfile`, not against those workflow files.
